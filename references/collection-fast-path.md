# 稳定分批采集

本文件只调整采集，不替换页面构建器、叙事、真实图片要求、三板块或验收。目标是减少重复的模型/浏览器往返，不承诺固定分钟数。

## 1. 首屏先保存

先识别淘宝或京东，再通过当前宿主支持的正常浏览器能力打开对应订单入口，用户登录和处理验证。核验账号别名、当前第1页及实际筛选范围；范围仍用用户指定或执行日前十年。单项目单平台，京东用 `project_meta.platform="jd"`，淘宝用 `"taobao"`；平台不符不覆盖旧项目。

淘宝默认不来回操作日期控件，先保存正常全部列表，再逐页读取、本地按 `requested_range` 过滤。京东默认近3个月，需按正常年份入口逐窗覆盖请求范围；先正常逐屏滚动，让本页商品图加载后保存。京东窗口与游标规则见 [京东采集分支](jd-collection.md)，不能把一个窗口终点当十年终点。筛选失败先暂停复核，不改变用户范围。两者都不能凭一页的首尾日期或页码按钮露出数量提前结束。

## 2. 能用预制适配器才用

`scripts/taobao_adapter.py` 与 `scripts/jd_adapter.py` 分别解析正常订单页面；对应采集器 `collect_taobao.py` / `collect_jd.py` 管稳定快照、批次和断点。不登录、不读Cookie、不请求私有订单接口、不用JS点击。选择器只是一份曾被观察到的页面结构，当前任务必须先小样本核验。

仅当宿主的浏览器说明允许这种DOM读取，且同一执行环境能接收并落盘结果时使用下例。`bu.js` 表示宿主提供的只读DOM能力，`advance_page` 必须是已核验的正常UI翻页回调；不是要求安装某个固定MCP。若宿主不提供此协议，使用原有正常逐页读取、规范化与落盘流程，不另起浏览器或私自连接CDP来绕开限制。

以下接口示例属于淘宝分支；京东按 [独立采集规则](jd-collection.md) 接入，不把淘宝适配器用于京东：

```python
from collect_taobao import configure_browser, collect_browser

# source在Skill目录外；先准备project_meta.json，platform=taobao及requested_range。
print(configure_browser(bu, source, account_key='已核验账号的本地别名'))
# first_page_saved=true才表示首屏保存；不得丢掉除两笔样本之外的首屏订单。

def advance_page(bu, target_page):
    # 此处由Agent接入当前宿主已观察并验证过的正常“下一页”操作。
    host_normal_next_page(bu)

print(collect_browser(bu, source, advance_page, max_pages=1, deadline_seconds=20))
# 核对页码推进、订单集合变化和落盘后，才扩大：
print(collect_browser(bu, source, advance_page, max_pages=5, deadline_seconds=45))
```

列表串行、相邻新页间隔至少4秒；默认5页/45秒，上限10页/120秒。批次预算不能打断宿主内部卡死的调用，外层也要使用宿主支持的超时。不要为了提速增加并发翻页、删冷却或一次跑全部页。每批只返回计数、耗时、状态、游标，不逐页打印全部DOM/订单，也不要求用户每批回复继续。

## 3. 保存与续跑

`orders.json` 保存成功的规范订单：淘宝为父订单，京东为实际子订单卡片，ID保留字符串，一单多件不重复计钱。`collection-cache/`先保存规范页，再原子更新订单和`collection-state.json`；中断后缓存重放，不重复网络读取。平台、账号别名和范围与断点绑定，页码/窗口及行标识策略不可静默切换；`collection-metrics.json`记批次指标。它们留本地，不进入公开仓库或网页发布包。不要保存整页HTML、地址、聊天或凭据。

状态：

- `ready`：继续下一批；`cooldown`：按wait_seconds等候，不再叠加固定sleep。
- `complete`：核验了正常列表可访问终点；不代表平台隐藏记录也齐全，不自动将coverage写成十年完整。
- `verify_boundary`：空页/空容器先人工或正常UI核验；仅允许一次新读复查，仍不明确就如实记缺口。
- `handoff`：验证、登录失效、限流、未知结构、不推进或工具异常。保存进度暂停，不跳页或自动清除失败。

阻挡正常解决后，使用对应平台采集器的 `resume_browser`，记录实际重新核验结论。浏览器须停在待保存页或其前一页；不同位置先通过正常UI定位，不能改游标冒充已采。平台、账号或过滤窗口变化先停下复核，不能沿用另一个平台/账号/范围的断点；京东的正常窗口切换由平台采集器按已核验的边界推进。单个目录只允许一个采集/回填进程。

双快照核对页码、订单ID集合与内容指纹；页码先变而列表未更新时不提交新页。默认不凭日期提前停止，因为列表排序未必严格。数量看不清不能默认1；缺项先核对该商品行。缺实付/退款保持null，不用标价或0补齐。日级日期用`date_precision=day`，午夜仅作日期容器，不能说是实际下单时间。

淘宝多商品默认订单内稳定行序号；只有现场确认行序变化、且每行都能取得唯一真实商品ID时，才显式选`item_id_basis='item_url'`，并与断点绑定。京东按其适配器保留真实商品ID与行身份；相同商品不同规格也不能仅凭商品ID合并。列表重读保留核验过的秒级时间、已知金额/退款与同源已下载图片。京东无实付标签的列表金额仅为 `observed_amount`，不是实付或净支出；拆单父横幅总额不重复下发给子单。

## 4. 详情与图片

不逐单打开详情：列表字段已够时直接保存，详情只补金额冲突、关键缺项、小样本核验或已选主视觉的同商品清晰图。未知退款不触发全量详情。列表缺图如实记缺失，不凭商品名找相似图。

待当前订单批次落盘后，再下载图片；下载与采集不可同时改orders.json。先核验1—3个真实源URL、图片内容及精度，将实际观察的精确图片主机列入允许列表，不猜高清URL、不删签名/规格后缀。

```bash
python scripts/manage_media.py "数据目录" plan --allow-host 实际已核验的图片主机
python scripts/manage_media.py "数据目录" download --workers 3 --max-mb 512 --max-file-mb 25
```

同URL合并下载、内容SHA256去重，成功文件复用，最多2次网络尝试；401/403/429/432停止新任务，保留已成功文件。预算不足保存断点并报告，不减图、不强压清晰度。记录每商品image_path/status/sha256/尺寸；HTML、空响应或错规格不能当成功。下载失败可单补，不重抓全部订单。完整图源都入队；不是只下载首页4张。需要主图清晰度但源图不足时按原规则补同一商品正常页面的图。

`media-download-report.json`区分完成/失败/待下载/缺源，不能用文件数证明完整。下载后仍按原规则逐张查看选入叙事的图片、填写story.visuals、各板块image_paths，运行原构建和浏览器验收。下载提速不能变成有图不展示或纯文字页面。

## 5. 对比口径

记录相同平台、账号/范围、页数/成功订单数、商品行数、已下载和渲染图片数、缓存冷热、批次次数、耗时和未解决缺口。断点复用只说明少做重复工作；合成测试只证明程序行为，不能冒充真实平台或某模型的15分钟端到端测试。
